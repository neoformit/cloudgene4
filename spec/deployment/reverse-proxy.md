# Reverse proxy (nginx)

## Purpose

nginx terminates TLS in front of gunicorn, redirects plain HTTP to HTTPS, forwards the client's
host and scheme so Django can build correct URLs and enforce HTTPS, and is the first layer to
see a request body. This file specifies the example site configuration
`deploy/nginx.conf.example`, which security headers come from which layer (nginx or Django), the
Content-Security-Policy the SPA needs, and how errors nginx itself generates must look to the SPA.

## Scope

Covered:

- `deploy/nginx.conf.example` (both `server` blocks).
- Security response headers wherever they are set: Django `SecurityMiddleware` /
  `XFrameOptionsMiddleware` settings in `cloudgene_django/settings.py:119-130,229-255`, and the
  planned Content-Security-Policy.
- HSTS settings and the silenced `security.W021` check (`cloudgene_django/settings.py:237-255`).
- Errors generated by nginx (413, 502, 504) for `/api/` paths.

Out of scope:

- gunicorn settings and the upload size chain: [web-server.md](web-server.md) (this file owns only the
  nginx links of that chain).
- Static file caching policy: [static-assets.md](static-assets.md).
- Cookies, CSRF trusted origins, `ALLOWED_HOSTS`, `check --deploy` checks other than HSTS:
  [security-hardening.md](security-hardening.md).
- Certificate issuance/renewal (Certbot) and nginx installation: [install-upgrade.md](install-upgrade.md).
- The per-download `Content-Security-Policy: sandbox`: [../backend/jobs-api.md](../backend/jobs-api.md) (BE-JAPI-021).

## Requirements

### TLS and redirect

- **DEP-PROXY-001** A plain-HTTP request on port 80 MUST receive `301` to
  `https://$host$request_uri`, except paths under `/.well-known/acme-challenge/`, which MUST be served
  from the ACME webroot over HTTP.
- **DEP-PROXY-002** The HTTPS server MUST accept only TLS 1.2 and TLS 1.3.
- **DEP-PROXY-003** The HTTPS server SHOULD enable HTTP/2.
- **DEP-PROXY-004** gunicorn's port MUST NOT be reachable from outside the host; nginx MUST be the only
  client-facing listener (see DEP-WEB-002).

### HSTS

- **DEP-PROXY-005** nginx MUST NOT add its own `Strict-Transport-Security` header, so the policy
  has one source and one value. The header itself, its value and the preload policy are owned by
  [DEP-SEC-012](security-hardening.md#requirements) and
  [DEP-SEC-008](security-hardening.md#requirements).
- **DEP-PROXY-006** (withdrawn — see [DEP-SEC-012](security-hardening.md#requirements))
- **DEP-PROXY-007** (withdrawn — see [DEP-SEC-012](security-hardening.md#requirements))
- **DEP-PROXY-008** (withdrawn — see [DEP-SEC-008](security-hardening.md#requirements))

### Proxy headers

- **DEP-PROXY-010** Every proxied request MUST carry `Host: $host`, `X-Forwarded-For`,
  `X-Real-IP` and `X-Forwarded-Proto: $scheme`, and use HTTP/1.1 to the upstream.
- **DEP-PROXY-011** Django MUST treat a request as secure from `X-Forwarded-Proto: https` only when
  `DJANGO_BEHIND_TLS_PROXY=1`. With that and `DJANGO_SECURE_SSL_REDIRECT=1`, an HTTPS request through
  nginx MUST NOT be redirected again (no redirect loop), and absolute URLs Django builds (for
  example account e-mail links without `server.url`) MUST use `https://` and the client's host.

### Body size and errors

- **DEP-PROXY-012** `client_max_body_size` MUST satisfy DEP-WEB-031
  (`≥ server.max_upload_mb + 10 MiB`).
- **DEP-PROXY-013** (planned) When nginx rejects a request under `/api/` for body size, the response
  MUST be `413` with `Content-Type: application/json` and the error envelope: `code`
  `upload_too_large`, a `message` that states the limit, and empty `fields`. Requests outside
  `/api/` MAY keep nginx's default page.
- **DEP-PROXY-014** (planned) When nginx cannot get a response from gunicorn for a request under
  `/api/` (502, 504), it SHOULD return the error envelope with the same status and code
  `server_error`, so the SPA never parses an HTML error page.

### Timeouts

- **DEP-PROXY-015** `client_body_timeout`, `proxy_send_timeout` and `proxy_read_timeout` MUST each be
  at least 300 s, and `proxy_read_timeout` MUST be at least `GUNICORN_TIMEOUT` (DEP-WEB-011).

### Static files and compression

- **DEP-PROXY-016** nginx MAY serve `/static/` directly from `STATIC_ROOT`; if it does, it MUST apply
  the cache policy in [static-assets.md](static-assets.md) (DEP-STATIC-020..022), and MUST NOT give
  `index.html` a long cache lifetime.
- **DEP-PROXY-017** (planned) Text responses for static assets (JavaScript, CSS, SVG, JSON source
  maps) SHOULD be served compressed (gzip or brotli) to clients that accept it.

### Security headers

- **DEP-PROXY-020** Every HTML response from the application MUST carry `X-Frame-Options: DENY`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin` and
  `Cross-Origin-Opener-Policy: same-origin`. These MUST be set by Django; nginx MUST pass them
  through unchanged.
- **DEP-PROXY-021** (planned) Every response that serves the SPA shell (`spa_index`) and every page
  under `/django-admin/` MUST carry a `Content-Security-Policy` header that at least: allows script
  only from `'self'` (no `'unsafe-inline'`, no `'unsafe-eval'`), sets `object-src 'none'`,
  `base-uri 'self'` and `frame-ancestors 'none'`. Markup injected through `v-html`
  (page HTML, workflow descriptions — FE-PAGE-031, FE-PAGE-033) MUST therefore not execute inline
  `<script>` or event-handler attributes.
- **DEP-PROXY-022** (planned) The Content-Security-Policy MUST be set by Django (one home, present
  whether or not nginx is in front), not by nginx. `deploy/nginx.conf.example` MUST NOT add a
  `Content-Security-Policy` header.
- **DEP-PROXY-023** (planned) Adding the global policy MUST NOT remove or relax the
  `Content-Security-Policy: sandbox` that every `jobs_outputs_retrieve` response carries
  (BE-JAPI-021).
- **DEP-PROXY-024** (planned) The policy MAY be relaxed only for `/api/schema/swagger-ui/` (which
  loads Swagger UI from a CDN with an inline bootstrap script); any relaxation MUST be limited to
  that path.
- **DEP-PROXY-025** nginx SHOULD set `server_tokens off`.

### Planned Content-Security-Policy (DEP-PROXY-021)

Starting policy for the SPA and `/django-admin/`:

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
font-src 'self' data:;
connect-src 'self';
object-src 'none';
base-uri 'self';
frame-ancestors 'none';
form-action 'self'
```

- `style-src 'unsafe-inline'` is needed because templates and `v-html` content use `style`
  attributes (33 `style=` occurrences in `frontend/src`). It does not enable script execution.
- The production bundle loads only same-origin modules (`/static/frontend/assets/…`) and makes
  only same-origin API calls; Vue's runtime build needs no `'unsafe-eval'`.
- Django 6.0 provides `SECURE_CSP` / `SECURE_CSP_REPORT_ONLY` with
  `django.middleware.csp.ContentSecurityPolicyMiddleware`; that is the intended home. Roll out as
  report-only first, then enforce.

### Planned nginx 413 for `/api/` (DEP-PROXY-013)

```nginx
location /api/ {
    error_page 413 = @api_too_large;
    # ... same proxy_* settings as location / ...
}
location @api_too_large {
    default_type application/json;
    return 413 '{"error":{"message":"The request is too large (max 1034 MB).","code":"upload_too_large","fields":{}}}';
}
```

The limit in the message is the configured `client_max_body_size`; it has to be kept in step by
hand, like the directive itself.

## Behaviour

**Request path.** Browser → nginx :443 (TLS) → gunicorn `127.0.0.1:8000` (whitenoise for
`/static/`, Django for everything else). Port 80 only redirects and serves ACME challenges.

**Scheme detection.** nginx sets `X-Forwarded-Proto $scheme` (always `https` on the 443 block).
Django reads it via `SECURE_PROXY_SSL_HEADER` when `DJANGO_BEHIND_TLS_PROXY=1`
(`settings.py:246-247`); gunicorn separately trusts it only from `GUNICORN_FORWARDED_ALLOW_IPS`.
If gunicorn were reachable directly, a client could send `X-Forwarded-Proto: https` over HTTP and
be treated as secure by Django — hence DEP-PROXY-004.

**HSTS.** Policy: [DEP-SEC-012](security-hardening.md#requirements) and
[DEP-SEC-008](security-hardening.md#requirements). nginx-generated responses
(redirects on port 80, 413, 502) carry no HSTS header; that is acceptable since browsers record
HSTS from any successful HTTPS response.

**Oversized body today.** nginx compares `Content-Length` (or the streamed size) with
`client_max_body_size` and answers `413` with its own HTML page before contacting gunicorn. The
SPA's `apiErrorMessage` finds no envelope and, for a status below 500, returns the caller's
fallback: the submit form shows `Job submission failed.` with no size hint (FE-FORM-030). Some
browsers report the connection reset before reading the 413 at all, in which case the SPA shows
`Cannot reach the server. Check your connection.`

**Upstream failures today.** A gunicorn worker killed by `timeout`, or gunicorn down, gives
nginx's HTML 502/504. The SPA shows `Server error. Please try again later.` (status ≥ 500). This
is acceptable to users, but contract tests that assume every `/api/` response is JSON do not hold
behind nginx.

**CSP today.** No layer sets a global `Content-Security-Policy`. Admin-authored page HTML and
workflow descriptions from installed repositories are rendered with `v-html` on the app origin;
a `<script>` element inserted by `v-html` does not run, but event-handler attributes
(`<img onerror=…>`) do. The only defence today is trust in admins and workflow sources
(plans/QA_FINDINGS.md I-2, I-3; BE-SRV-012).

## Open questions

1. CSP versus sanitising: should page HTML and workflow descriptions also be sanitised
   (server-side allow-list) in addition to the CSP? Same question as
   [../backend/admin-api.md](../backend/admin-api.md) open question 3 and
   [../frontend/home-static-pages.md](../frontend/home-static-pages.md) open question 1. CSP alone
   does not stop injected markup that only changes appearance (phishing-style content).
2. Should `img-src` allow `https:` so admins can embed external images in page HTML? Each allowed
   origin weakens the policy.
3. Swagger UI: exempt `/api/schema/swagger-ui/` from the policy (DEP-PROXY-024), self-host its
   assets (`drf-spectacular-sidecar`), or disable it in production?
4. The error code table has no code for upstream failures; should 502/503/504 envelopes
   (DEP-PROXY-014) use `server_error` or a new `service_unavailable` code?
5. Compression of `/api/` JSON responses that echo secrets (CSRF token is in a cookie, not the
   body, so BREACH exposure looks low): enable gzip for `application/json` or restrict to static?
